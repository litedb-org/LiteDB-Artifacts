# External review of the durability design (ChatGPT Pro, relayed by the owner, 2026-09-28)

Reviewed: published cee8bb3ee sources and decisions (no build or test run; unpushed work assessed from a description).

1. The strict WAL-removal gate is necessary, but does not establish crash consistency (corruption). Two ordering barriers: durable recovery information -> overwrite data pages -> durable data -> discard recovery information. Rule 1 enforces the second. A checkpoint still lets an unsupported WAL sync degrade and then writes data pages (DurableFlush.cs:191-249, HeaderJournal.cs:11-35, WalIndexService.Checkpoint.cs:180-225). Scenario: opted-out transaction changes P and Q; its WAL and header journal exist only in cache; checkpoint writes P; power fails before Q or the recovery information persists. Recommendation: checkpoint must refuse before the first data overwrite unless the WAL, journal and their namespace are durably recoverable, even with durable commits=false. This also disproves decision 9's claim that an unsyncable WAL directory affects durability but not consistency. SQLite NORMAL keeps checkpoint barriers; PostgreSQL distinguishes async commit from fsync=off.
2. "Invariant I" does not justify trusting a valid header in a fresh process. Scenario: process A creates a database, header sync unsupported, leaves an unanchored WAL (opted-out writes); process B trusts the valid cached header, syncs more WAL commits; power loss removes the header or file length. The constructor initializes an empty data file before validation (DiskService.cs:69-96). Recommendation: keep rejecting nonempty unanchored WAL + unprovable header; recover existing evidence before initialization, including zero-length and partially initialized files.
3. A genuine sync failure requires recovery, not reopening and retrying (fsyncgate). Backfill writes P and Q; sync reports EIO; the kernel drops the dirty pages; a later sync succeeds; the counter gate allows WAL removal. Separate: known unsupported capability; capacity/admission rejection before I/O; actual write-back failure with uncertain state, which invalidates durability proofs and requires validated replay/rewrite before writable recovery. Default A should depend on which operation failed and what depends on it. Scrutinize classifying EROFS and UnauthorizedAccessException as "cannot sync".
4. The anchor should be a generation recovery record, not a skipped transaction frame. It must never become reusable capacity, be discarded as an unconfirmed tail, be included in digests, or override a newer required retirement root. Startup must resolve header, journal, anchor and WAL generation consistently, including valid-but-different headers. An outstanding footer blocks appends. Prefer a versioned immutable recovery record at the start of every WAL generation; keep WAL-only mode non-reclaiming until data durability is established.
5. Proof "once per log path per process" is too weak: a path is not a file incarnation (rebuild replaces files at the same names). Associate proofs with the file incarnation and WAL generation; invalidate on create/delete/rename/rebuild. Preflight cannot guarantee "fails before any WAL frame is written": later failure means outcome unknown. Rewrite that guarantee.
6. Lazy read-only reopening needs a lifetime protocol: a thread holding a cursor on the old engine while another triggers the reopen and disposes it. Publish failure while holding write admission, quiesce or invalidate outstanding transactions/cursors before disposing, exactly one reopener, Dispose never triggers reopening. Define how other connections/processes are fenced. Reads only from a validated consistent snapshot.
7. A commit that threw may legitimately reappear; suppressing it is dangerous. All frames and the confirmation reach the kernel; sync fails; recovery sees a complete transaction. That is an ambiguous commit. Return a dedicated outcome-unknown error; applications need idempotent identifiers or an outcome query. Do not erase valid confirmations to make "exception means rollback" appear true. Change decision 6's "don't throw unless it was the caller's own commit": a failed caller-requested Insert, safepoint, explicit checkpoint or flush must not return success. Suppressing an automatic checkpoint exception after a durable commit can be appropriate.
8. Encryption is a separate bootstrap problem. AesStream's constructor durably flushes writable streams, so durable commits=false does not restore writable access on #2242 storage for encrypted files. Either exclude encrypted WAL-only creation or design recovery of the encryption preamble together with the header. Read-only anchor recovery should use an in-memory overlay. Encrypted-WAL creation authenticates the data source before completing an interrupted WAL preamble; missing-data recovery must address that ordering.
9. The write-count gate needs coverage at the actual mutation boundary (partial failures, header writes, length changes, encryption metadata, recovery, promotion, error markers); serialize the sync boundary with mutations; the gate must also govern interior reuse, witness publication, journal retirement, tail repair and file replacement.
10. The WAL limit: default D correct; B reasonable for actual disk-full; reaching a configured limit before I/O should not poison the engine; C needs validated recovery. RebuildService disables checkpoints while importing the replacement: a 1 GiB limit can reject larger rebuilds on healthy storage. Reserve capacity before WAL extension, keep emergency space for recovery. On storage where neither barrier works, opting out cannot give indefinite bounded crash-consistent writing: writes must eventually stop or the contract must permit corruption.
Also: state the power-safe-overwrite assumption (8,256-byte frames share sectors; checksums do not protect previously synced neighbouring bytes from collateral tearing) as part of the durability contract. Merge gate should exercise fresh processes, independently persisted contents and directory entries, repeated recovery crashes, encryption, shared engines and retained readers.
