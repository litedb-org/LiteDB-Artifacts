# Second opinion on the durability policy (#3027) — read-only review of HEAD 6a128f367

Overall: decisions 1, 3, 5, 6, 9 and defaults A–D are sound and mostly match what SQLite/RocksDB/PostgreSQL do. The weak spot is the whole "is the data header on the device?" machinery (implementation note 1, decisions 8/10, `DurableHeaders`, "invariant I"). It exists only because LiteDB's WAL is not self-describing (the salt lives in the data header and is copied into frames). Fixing that root cause is simpler and safer than the conditional anchor. Findings, most important first.

## 1. An empty data file beside a non-empty WAL is silently re-initialized (data loss, silent)
`DiskService.cs:71-94`: `dataLength == 0` → `Initialize` (new random salt), with no look at the log. Then `WalIndexService.RestoreIndex` → `WalChecksum.Validate` salt mismatch → `WalRecovery.InvalidTail` → `DiscardWalTail` (`DiskService.Checksums.cs:136-149`) → `SetLength(0)` bypassing the shrink gate. The database opens "healthy" and empty; every frame is gone.
Concrete in-scope scenario: database created on #2242 storage (`Initialize.cs:43` sync answers "cannot sync", header stays in the OS cache), commits with `durable commits=false` (`RequireDurableCommit` returns at `CommitDurability.cs:23`, no anchor), power loss → data file 0 bytes, WAL intact (the OS wrote it back). Also: a durable session on such storage *before* the anchor lands, and any torn anchor. Decision 8's "only when someone else deletes files" is not true here.
Fix (independent of the anchor): a writable open must refuse to initialize when a log with content exists (mirror `RejectConvertedWal`, `Validation.cs:64-83`: "move the log aside or restore"); read-only opens already refuse. With an anchor present, recover from it instead. This is cheap and should ship before anything else.

## 2. Replace the conditional anchor + `DurableHeaders` with an unconditional WAL header record per generation (design)
SQLite's WAL header (magic, salts, checksum) makes the WAL validate itself; the db header only says which generation is current. The plan writes the anchor only "when the header is unproven", so correctness rests on (a) a process-wide `DurableHeaders` cache and (b) "invariant I". Both are weaker than a record that is always there:
- `DurableHeaders` (`DurableHeaders.cs:13-17`, `ProveDataFile` `DurableFlush.cs:322-329`) declares a hole: a `File.Copy` restore with a byte-identical header is taken as synced. That is not "someone else changing files while LiteDB runs"; it is a backup restore between opens in a long-lived process, and the outcome is a WAL that assumes restored pages the device may not have — corruption, not lost commits.
- Opt-out sessions leave an un-anchored WAL; a later durable session then throws until a checkpoint (which needs a sync that never comes on such storage).
- Shared mode pays a header read + SHA-256 per operation, plus one failing fsync per operation on #2242 storage.
Proposal: the first frame of every WAL generation (position 0, written by whichever write first extends an empty WAL, in both modes; synced under durable commits, flushed otherwise) is a checksummed header frame with a distinct trailer marker. Rules at open: data header valid and salt == record salt → normal; data header missing/torn and no journal applies → take the record's header (its salt validates the rest); data header valid with another salt → stale generation, discard (safe: `RotateWalSalt` runs only after the backfill sync succeeded, `WalIndexService.Checkpoint.cs:186-198,222`, so a valid newer header proves the backfill is on the device). Then `DataHeaderDurable`, `DurableHeaders` and "unproven" go away; `DurableLogs` stays (it proves the *log* syncs, a separate thing). Cost: 8256 bytes + one log sync per WAL generation, i.e. per full checkpoint — negligible next to the checkpoint's own syncs.
Implementation traps to note: `GetFileLength(Log) > 0` is used as "WAL non-empty" in `Checkpoint.cs:107`, `Dispose.cs:16`, `WalKeptReport`, `EmptyLog`; an anchor-only WAL must count as empty (else every close rotates the salt and the WAL is never deleted). `HeaderJournal.ReadIntent` reads position 0 (`HeaderJournal.cs:77-108`) but rejects it via the version byte; keep a test for that. The footer body CRC (`HeaderJournal.Checkpoint.cs:22`) hashes raw bytes before validation, so writer and verifier stay consistent if both read through `WalRetirementReader`.

## 3. "Invariant I" is true for this version's header writes, but the conclusion drawn from it is wrong
I checked every header write: `Initialize.cs:35-43` (sync may fail, no journal — the stated exception); `RotateWalSalt` `Checksums.cs:119-134` (a failed sync is caught by `EmptyLog`→`RequireDataWritesSynced`, `DataWrites.cs:68-84`, journal kept); `CompletePartialCheckpoint` `Retirement.cs:83-98`; `WriteFileVersion` `FileVersion.cs:63-106`; header repair `HeaderJournal.cs:102-119`; backfill of page 0 under the checkpoint journal; `MarkAsInvalidState` `DiskService.cs:208-240` (sync may fail, journal stays — fine). The plan adds a new unjournaled write (the anchor's header into the data file's OS cache at open); it is idempotent, fine.
But "a new process could trust a valid header it reads when no journal is pending" does not follow: the new process cannot tell the creation exception from a synced header, and cannot tell an opt-out session's unanchored WAL from a proven one. With the unconditional record of finding 2 the question disappears; with the conditional anchor, a valid header must be trusted only when the anchor is present and matches, or a data sync succeeds.

## 4. The read-only reopen can show a commit that threw (misleading; also one non-sticky path)
`WalWrite.cs:141-160`: frames and the confirmation reached the OS, `FlushConfirmedLog` fails, the engine stops; `ReopenAfterWriteFailure` (`LiteEngine.WriteFailure.cs:34-61`) replays the WAL from the files, so the transaction the caller saw fail is now visible in the same process. "Outcome unknown" is the honest answer for the *device* (PostgreSQL and SQLite say the same), but the in-process view should not flip. Recommend: pass the last acknowledged confirmed position (`_checksums.LastConfirmedPosition` before the batch) to the read-only reopen and recover only up to it; the next real open lets the device decide. Document the unknown-outcome semantics in the release notes.
Related inconsistency: an EIO from `RequireWalBelowLimit`→`DataFileSyncs()` (`WalLimit.cs:16`, `DurableFlush.cs:429`) propagates to the caller before `ExecuteAutoTransaction` enters its try block: not recorded, not sticky, engine continues — contrary to decision 6.

## 5. Decision D leaves #2242 users with an eventual outage and no escape hatch (usable)
On storage that never syncs, the WAL grows to `wal limit`, then every write throws forever; every open replays up to 1 GiB. That is safer than the dev-branch fallback (an OS-cache-only backfill + WAL emptying can leave a torn data file, i.e. corruption, not just lost commits), and better than 5.0.21 (whose checkpoint threw), so keep D as the default. But SQLite offers `synchronous=OFF` with a documented "corruption on power loss" warning, and that is exactly what these users had in dev. Recommend a separate, explicitly named unsafe option (not `durable commits=false`) that restores ordered OS-cache checkpoints; refuse it for encrypted files (preamble). Minor: each refused write retries a data sync under the WAL writer lock (`DurableFlush.cs:112-119`); cheap on EINVAL, but rate-limit it.

## 6. Sticky-failure mechanics: four concrete gaps (misleading / usable)
a) `Checkpoint()` after the reopen returns 0 silently (`LiteEngine.cs:407`, `_settings.ReadOnly ? 0`): the caller's explicit drain "succeeds". Throw `ReadOnlyWrite()` when `_settings.WriteFailure != null`.
b) Lost transactions are keyed by managed thread ID (`WriteFailure.cs:19,80-96`); pool threads reuse IDs, and a mark is consumed only by Commit/Rollback. A later unrelated `BeginTrans` on that ID returns false (`Transaction.cs:22`) and its `Commit` throws "an earlier write failed". Consume the mark in `BeginTrans` and throw the recorded failure there.
c) `Dispose` (`LiteEngine.cs:423-427`) does not take `_reopenLock`; `Close()` can run while `Open()` is assigning `_state/_disk/_walIndex/_monitor`, leaving the new `DiskService` undisposed (file handles leak, sharing violations on Windows). Take `_reopenLock` in `Dispose`.
d) `LiteEngine.cs:200` rebuilds on `AutoRebuild` without checking `_settings.ReadOnly`; a read-only fallback or reopen must never rebuild. Probably pre-existing; verify against 5.0.21.
The teardown/reopen handoff itself (`EngineState.BeginStop/CompleteStop`, `WaitClosed` 30 s, `_reopenLock`, stale-state check) is correct; other threads mid-operation fail with the stop error as documented.

## 7. `LogSyncUnverified` is a silent exception to decision 3 (misleading, rare)
`NativeFileSync.cs:67-73`, `DurableFlush.cs:72`, `CommitDurability.cs:51`: with no bindable libc, EIO and "cannot sync" are invisible and commits are acknowledged. musl and glibc are bound, so mainstream containers are covered; still, log it at open and consider failing the first durable commit with a clear message unless opted out, since the user believes they have durable commits.

## 8. Decision 3 proof design: sound
Once per log path per process, before the first frame, is the right shape: the only thing the proof buys over the commit's own sync is "not written" instead of "unknown", for one extra fsync per process per path. `DurableLogs.Forget` on a later "cannot sync" and the per-engine directory sync (`FlushLogToDisk` `DurableFlush.cs:237`) are correct. The log's directory sync also persists a newly created data file's name (same directory), which matters for finding 1 on local disks. Two notes: the proof is skipped while `_readOnly`, fine; the anchor of finding 2 would be written before the proof's frames, so "no frame written" should read "no transaction frame".

## 9. Strict WAL rule and the shrink gate: sufficient; one over-strict case (cost)
`ShrinkLog/EmptyLog/ReclaimLogPages` all go through `RequireDataWritesSynced`; the paths that bypass it (`DiscardWalTail`, the failed-append truncation in `WalWrite.cs:253-262`, `TrimTrailingPage`) remove only bytes no recovery reads. Correct and necessary (the WAL write-back-ahead-of-backfill hazard is real on non-syncing storage). Over-strict case: a full checkpoint completed (rotation synced) but the WAL truncation did not persist, and the storage stops syncing; the next process opens read-only forever (`HeaderJournal.cs:115-119`) although the WAL is provably stale. Rare; acceptable, but a stale-generation exemption is safe by the argument in finding 2.

## 10. fsyncgate: LiteDB is fine for a non-obvious reason — write it down
After an EIO, Linux marks pages clean; a new handle's fsync "succeeds" and PostgreSQL got burned. LiteDB survives because every reopen resets `_backfillVersion` and the next checkpoint re-copies every WAL page (re-dirtying them) before any emptying, and the engine never retries a sync on the failed handle (sticky). This must be stated as an invariant in `storage-stack-safety.md`; an optimization such as "skip pages already backfilled" would reintroduce the bug.

## 11. Smaller points
- `IsDurableFlushUnsupported` treats `UnauthorizedAccessException`/EACCES as "cannot sync" (`DurableFlush.cs:478-492`); in opt-out mode a permission failure is silently degraded. Low.
- `SharedDurabilityState` is per `SharedEngine`; two shared connections in one process do not share the sticky failure. Acceptable, document it.
- Explicit-transaction writes do hit `RequireWalBelowLimit` (via `ExecuteAutoTransaction`), good; the limit compares logical length, not raw bytes — fine.

## Comparison with mature systems (Q1)
SQLite WAL: self-describing WAL header with salts; `synchronous=NORMAL` = LiteDB opt-out (no per-commit fsync, checkpoint still syncs); `synchronous=OFF` = the missing escape hatch; fsync error → `SQLITE_IOERR_FSYNC`, no sticky state (worse than LiteDB). RocksDB: sync error → background-error state, writes rejected until `Resume()` = decision 6/C. PostgreSQL: PANIC + WAL replay on fsync failure = finding 10. Divergences: the WAL depending on the data header (not justified; finding 2), no unsafe mode (finding 5), a hard WAL limit (justified: it only bites while the data file cannot sync, long readers do not trip it).

## If I were designing this
Keep decisions 1, 3, 5, 6, 9, A–D. Make the WAL self-describing: a header record at the start of every generation, both modes; use it at open exactly as SQLite uses its WAL header; delete `DurableHeaders` and the "unproven header" state; keep the once-per-path log proof. Refuse to initialize over a non-empty log. Add an explicitly named unsafe mode for storage that never syncs, off by default. Keep sticky failures, but reopen read-only with recovery bounded to the last acknowledged confirmation, make `Checkpoint()` throw after a failure, key lost transactions by transaction rather than thread ID, and serialize `Dispose` with the reopen. Document "outcome unknown" and the full re-backfill invariant. Ship finding 1 first.
