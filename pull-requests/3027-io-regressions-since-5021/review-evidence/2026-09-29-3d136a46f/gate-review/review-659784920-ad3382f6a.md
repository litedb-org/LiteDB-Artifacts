### Confirmed findings, ranked

1. **A sync that cannot report failure still counts as proof of "NotCommitted"** (`DiskService.WalWrite.cs:360-365`).
   - `LogSyncUnverified` means Unix with no bindable C library, where `Flush(true)` loses fsync errors. In that case `SyncRawLog` still sets `_logBarrierSynced = true`, and the commit is reported NotCommitted.
   - The project treats such a sync as proving nothing: implementation notes 3 and 15, `RuntimeSyncDurability_Tests` ("a sync that cannot report failure proves no durability"), the guard in `ProveRetirementSyncs` (`DurableFlush.cs:161`) and slot reuse (`WalSlots.cs:91-92`).
   - Repro `Unverifiable_sync_still_reports_not_committed`: with `NativeFileSync.SimulateRuntimeSync = true`, `durableLogFlush` is false, and a throw at the `wal-confirmation-after-write` crash point gives outcome "NotCommitted".
   - Fix: `return _logBarrierSynced && !this.LogSyncUnverified;`, or skip the sync and return false. With that change, WrittenConfirmation, RuntimeSync and my repro all pass. Severity is low because it needs both a write failure and a silently failed fsync.

2. **The blank-sector tests would pass a weaker implementation** (test gap, HeaderFrame_Tests).
   - I changed `Completes` to compare only each sector's first 16-byte block with `BlankBlock`. All 36 HeaderFrame and rebuild-reader tests still passed.
   - The refusal test uses another database's sector, which decrypts to noise from its first block. Add a refusal row where a sector starts with the blank block and holds other bytes after it.

3. **A non-IOException write failure carries no outcome at all.** This predates these commits.
   - The fallback tag at `WalWrite.cs:171` only catches `IOException`. When `uncertain` ends false (truncation synced), an `UnauthorizedAccessException` propagates with no `LiteDB.CommitOutcome`. That exception is how .NET reports write EPERM/EACCES.
   - Repro `Non_io_write_failure_carries_no_outcome`: the crash point throws `UnauthorizedAccessException` and `Data` has no outcome key.
   - Decision 14 and the release notes say a failed commit carries its outcome.

4. **One of the two fixes in ad3382f6a has no test.** The commit message says a confirmation written before a later step failed was reported NotCommitted with the frame still there. That path (`readable != null`, no truncation) is not covered. My DiskService-level test (`WriteLogDisk` with a `written` callback that throws) confirms it now returns "Unknown". Worth adding to the PR.

### Plausible, not introduced by these commits

- **Race window for decision 6.** Some failures are recorded after the writer lock is released: `Transaction.cs:173` (`RecordWriteFailure("A commit")`) and `LiteEngine.WalLimit.cs:37-41` (`LogSyncs` then `StopAfter`). In that window another thread's batch can pass `RequireNoWriteFailure` and sync the same handle again. That already happens through `FlushConfirmedLog`; the new failure-path sync adds no new exposure.
- **Blank first block masks the whole page.** `AesStream.Read` zero-fills a whole read when its first block is blank, so an encrypted header whose sector 0 never reached the device is accepted whatever sectors 1-15 hold. The "15" test row passes before and after the change. I argue it is safe: a zero sector 0 means no header of that file ever synced, and decision 1 needs a data sync before a WAL generation ends. So no older generation can exist.
- **Rebuild version check ignores the header frame.** `RebuildService`'s constructor (`FileReaderV8.IsVersion`) throws InvalidDatabase when sector 0 was lost, plain or encrypted. It looks unreachable in practice because a writable open restores the header first.

### Checked, fine

- **(a) No remaining path reports NotCommitted for a recoverable confirmation**, apart from finding 1:
  - **Confirmations always append.** `AllocateLogPosition` never reuses a slot for a confirmation. A torn overwrite, an earlier buffered frame (`earlierHeld`), an outstanding header journal (no truncation) and a failed truncation all stay Unknown.
  - **Nothing after the confirmation can throw.** The producer's code after yielding it is trivial (`IsLast` reads ahead), and the delayed-confirmation (rebase) path goes through `WriteLogPage`.
  - **Header frame.** Its truncation needs no sync because it is not a confirmation.
  - **The truncated tail cannot be read back.** After truncation, at most 8,191 bytes of the removed frame stay in the padding, which can never form a complete 8,256-byte frame.
  - **Encrypted logs** hold no partial blocks in the CryptoStream (8,256 bytes is a whole number of blocks).
  - **Caller streams** (BufferedStream, HeldWrites): a torn held write surfaces as Unknown. Otherwise a non-FileStream "sync" is its `Flush()`, the same contract commits are acknowledged under.
  - **Shared mode** pays only on the failure path. Transaction IDs of abandoned frames are never reused.
- **(b) No sync where decision 6 forbids it.**
  - **Where the sync can run.** It runs only inside a batch that passed `RequireNoWriteFailure` under the writer lock. Earlier log syncs in the batch throw out of it (`RequireDurableCommit` records the failure; the rebase `FlushLogToDisk` propagates). A failed sync leads to Unknown, the record and `BeginStop` with no further syncs.
  - **No state is corrupted.** The raw sync without `Pad()` is safe because `SetLength` already page-aligns. `_logLength` is restored before the truncation, and `TrimCapacity` does nothing for files. `_logBarrierSynced` and the degraded flags are set accurately. The engine stops right after in every caller (commit and rollback both record and stop), so the WAL-limit, `RequireLogSynced` and `LogKnownUnsyncable` side effects never matter.
- **(c) The blank-block rule accepts exactly "the device holds zeros".**
  - **It is exact.** In ECB, a plaintext of repeated `D_k(0)` is the same as zero ciphertext, so the rule only accepts sectors that are zeros on the device.
  - **A real header sector cannot match by chance.** Its plaintext would have to equal the blank block in all 32 blocks, about 2^-4096.
  - **Stale and foreign sectors are still refused.** The protection is equivalent to the plain file's zeros rule.
  - **Right key.** `BlankBlock` comes from the file's own salt at the end of the AesStream constructor. The header sits at raw offset 8192, so sectors line up with blocks.
  - **Readers.** FileReaderV8 is covered, and no other reader needs the change.
- **(d) The ForgetfulFile power-loss model is correct.**
  - **`Image(until)`.** The prefix loop and the "until" mark are right: the mark is taken after the confirmation's pending write, so the image includes the confirmation and excludes the later truncation. Syncing before the truncation, or never syncing, fails the tests.
  - **Weaker spot.** Test 2 only counts syncs, but test 1 checks the ordering.
- **(e) Docs are accurate, with small nits.** Decision 14 and the release-notes wording "failed before its confirmation → NotCommitted" is not unconditional: a torn overwrite or a held buffered frame gives Unknown. The Unknown list covers this only loosely ("left a frame behind"). The `HeldWrites.Heard()` comment "nothing more is written or synced through the handle" is now contradicted by the truncation (older) and the new failure-path sync. Decision note 9, `page-and-wal-checksums.md` and `CommitOutcomeDataKey` are accurate.
