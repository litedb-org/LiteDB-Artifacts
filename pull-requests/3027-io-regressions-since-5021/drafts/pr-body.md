This PR fixes IO-layer regressions against LiteDB 5.0.21, plus the I/O safety defects that reviewing them turned up. The first commit (`e8785c4d6`) adds tests under `LiteDB.Tests/Regressions/` that assert the 5.0.21 behaviour and fail on `dev`. The later commits fix those regressions and everything found in the rounds of independent review and the owner's review (#3034 gates). Every new fixture (`LiteDB.Tests/Resources/*_5_0_21.zip`, `Vectors_6_0_0_prerelease_114.zip`) was written by the released package it is named after.

Two test categories:
- `RegressionSince5021`: the test asserts 5.0.21's behaviour and fails on `dev` (a few rows per class are controls that pass on both).
- `IoSafety`: an I/O safety defect found in review that is not a regression since 5.0.21 (present on `dev`, or introduced and fixed within this PR, such as `LegacyWalTornTail`).

Every fix was mutation-checked: reverting or weakening it makes its tests fail.

## Behaviour changes worth reviewing
- **Engine stops.** A WAL write failure that may have left a torn frame stops the engine whatever the exception type (5.0.21 rolled back and kept going after a non-I/O failure), as does a failed checkpoint, now before it releases the WAL writer.
- **Caller streams other than a `MemoryStream`** (a `BufferedStream`, a caller `FileStream` or `TempStream`) are flushed after every write, data and log: one `Flush()` per page write (a `FileStream` hands its buffer to the OS, without an fsync; a custom stream whose `Flush()` syncs or uploads pays that per page instead of per batch). A data sync that fails with an I/O error during the new data proof fails that operation and stops the engine (before, a data EIO only affected checkpoints).
- **Rollback-only transactions.** After a failed safepoint write, reads and writes in the transaction throw and `Commit` rolls back and throws.
- **Refusals (both files byte-identical):** `LOCK_TIMEOUT` for a blocked conversion (an unreadable reader registry is permanent until fixed, though callers usually retry this code); `IOException "Cannot convert this legacy database now…"` when the data file stopped syncing after the log synced commits; `INVALID_DATABASE` for a converted WAL beside a legacy header, and for a committed legacy WAL page that is not a page of its type, lies beyond both files, or is another database's header.
- **`AutoRebuild`** rebuilds in the same open that detects damage (`Issue2417_Tests`, `Issue2812Recovery_Tests` updated). Caller streams are never rebuilt.
- **Non-writable streams** holding a 5.0.21 file (or one needing repair) open read-only; read-only engines never write to their streams, not even the invalid-state mark.
- **Storage that cannot sync** never retires WAL frames. After its data file answered "cannot sync", the log is only flushed to the OS cache until a data sync succeeds (each log sync retries it first; commits were already reported non-durable then). A WAL whose frames the process synced before is kept and grows until the data file syncs again (automatic checkpoints wait for that data sync); otherwise full checkpoints keep the WAL bounded. A rebuild runs as where neither file syncs; a 5.x conversion whose drain keeps such a WAL is refused with an `IOException`.
- **Salvage:** a kept partial document reads like a complete one; a unique index gets its missing key as null, so a later document without that field conflicts with it.
- **fsync cost on storage that syncs** (counted with the sync hook; `dev` baseline from the owner's review):

  | Shared mode, per operation | 0 + 1 | 0 + 1 |

## Known residuals (documented)
- **While the data file cannot sync, a checkpoint's header journal is not synced either** (as where neither file syncs): a header write torn by a power loss then has no durable journal to repair it.
- **Process-wide durable headers** assume a file at the same path with the same header is the same file: a copy restored over it with a byte-identical header is taken as synced, so whoever replaces a database file must sync it (release notes; `FreshEngineDurability_Tests` pins both sides). Binding the cache to one open file lifetime instead would add a data fsync per direct-mode open and per shared operation.
- **Power-loss models** keep each file as of its last successful sync: one state per crash; they do not produce unsynced writes reaching disk in a partial or reordered subset across the two files, nor torn pages.
- **Repairing a torn header after an unsynced truncation:** the journal sync that repairs a torn header must precede every data sync, so it can make an earlier engine's unsynced WAL truncation durable ahead of that truncation's backfill. This needs two degraded episodes (storage that stopped syncing during a full checkpoint, and again during a later checkpoint that tore the header).
- **After a process restart, the OS writing an emptied WAL back ahead of its backfill:** the process remembers a WAL with synced bytes by its path (the next engine and shared operations keep it), but a new process cannot know which frames an earlier one synced, so on storage whose data file cannot sync it may empty such a WAL (its log syncs wait for the data file, so the model's power loss keeps them).
- **A rebuild on storage that cannot sync** installs its replacement without a power-loss guarantee, like every write there; the original files stay under their `-backup` names.
- **Caller data streams other than a `FileStream`** are not proven before a fresh engine's first log sync (a memory stream has no power loss; a custom stream shared by several engines is the caller's to sync). A caller stream whose `Flush()` does not write out what it holds is not protected against torn frames, nor is one that replays a failed write at another position (a `BufferedStream` over an inner stream that advances past the bytes it stored before failing; a `FileStream` does not), as in 5.0.21.
- **A foreign legacy WAL** that commits no header (a transaction that allocated no page) within the page bound, or that belongs to another copy of the same seed file (same creation time), is still replayed, as in 5.0.21.
- **The WAL writer's journal guard** is now behind the checkpoint's stop and is reached in tests only through a hook that restores the old stop timing.
- **Pre-existing on `dev`, not changed here:** a commit racing a concurrent `Rebuild` can throw `ObjectDisposedException` after committing (`TransactionMonitor.ReleaseTransaction` releases the transaction lock before its thread-local slot); seen once as a flaky `FuzzingContract_Tests` failure.
