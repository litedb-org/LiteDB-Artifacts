## Summary

This PR fixes IO-layer regressions against LiteDB 5.0.21, plus the I/O safety defects that reviewing them turned up, and implements the owner's durability decisions ([`docs/decisions/durability-policy.md`](https://github.com/litedb-org/LiteDB/blob/claude/compassionate-knuth-m52zj6/docs/decisions/durability-policy.md), decisions 1 to 14 with defaults A to D; all implemented, see "Durability decisions" below). The first commit (`e8785c4d6`) adds tests under `LiteDB.Tests/Regressions/` that assert the 5.0.21 behaviour and fail on `dev`; the later commits fix those regressions and everything found in the rounds of independent review, the owner's review (#3034 gates) and two external reviews. Every new fixture (`LiteDB.Tests/Resources/*_5_0_21.zip`, `Vectors_6_0_0_prerelease_114.zip`) was written by the released package it is named after.

Two test categories:
- `RegressionSince5021`: the test asserts 5.0.21's behaviour and fails on `dev` (a few rows per class are controls that pass on both).
- `IoSafety`: an I/O safety defect found in review that is not a regression since 5.0.21 (present on `dev`, or introduced and fixed within this PR).

Every fix was mutation-checked: reverting or weakening it makes its tests fail.

## Safety / regression evidence

- **Contracts and risk:** `durable-ack` (a commit acknowledged durable survives a power loss; one that cannot be made durable fails loudly before it writes; outcome-unknown commits are marked), `recovery-generation` (recovery never mixes data and WAL generations: header frame, header journal and salt rules, a WAL never initialized over), `reader-snapshot` (retired-slot reuse and the read-only reopen keep every reader's snapshot) and `historical-input` (5.0.21 files and WALs, v8 to v13 files and 6.0 prerelease vector files open, convert or are refused unchanged). What intentionally changes is listed under "Behaviour changes worth reviewing", each with its decision; the risk is concentrated in the WAL, checkpoint and recovery code (`LiteDB/Engine/Disk/*`, `WalIndexService.Checkpoint.cs`, `LiteEngine*.cs`, `EngineState.cs`).
- **Prior states and interactions:** 5.0.21 data files with and without their legacy WAL (also torn, foreign or beside their own conversion's WAL), damaged 5.0.21 documents, v10 to v13 files, WALs written before the header frame (no header frame: recovered as before), encrypted files, caller streams (`FileStream`, `BufferedStream`, `MemoryStream`, non-writable), direct and shared mode (several connections and processes), `durable commits` on and off, storage that answers "cannot sync" (#2242) for the data file, the log or the WAL directory, and storage whose sync fails with an I/O error. Older 6.x prereleases do not read the header frame (out of scope per the owner).
- **Failure outcomes:** a write or sync that failed is recorded and sticky: the engine continues read-only (reads keep working, writes throw the recorded failure, `$database.writeFailure` reports it) until reopened (decision 6); a failed commit carries `Exception.Data["LiteDB.CommitOutcome"]` (`NotCommitted` or `Unknown`), and the read-only reopen shows only acknowledged commits while the files are as the failure left them (decision 13); a refusal before anything was written is no failure. No WAL, header journal or legacy header backup is removed before a data sync covered every data write (decision 1). No in-place overwrite happens behind a recovery copy the log could not sync, in either mode (decision D, note 12): a checkpoint writes nothing and keeps the WAL, up to `wal limit` (decision 4). Every WAL starts with a header frame, and an open restores a data header the device lost from it or refuses unchanged (decision 11).
- **Evidence:** by failure model: `modeled-power-loss` (`FilePowerLossModel`/`SyncPowerLossModel` keep each file as of its last successful sync; `ForgetfulFile` forgets pages a failed sync marked clean): `HeaderFrame_Tests`, `HeaderFrameCrash_Tests`, `SyncFailureRecovery_Tests`, `OverwriteBarrier_Tests`, `RetiredSlotPowerLoss_Tests`, `SlotReuseWithoutProof_Tests`, `UnsyncedBackfillPowerLoss_Tests`, `KeptWalStop_Tests`, `DataFileStopsSyncing_Tests`, `FreshEngineDurability_Tests`, `FreshEngineLogSync_Tests`, `CompactPromotionPowerLoss_Tests`, `WrittenConfirmation_Tests`; `process-death`: `HeaderFrameCrash_Tests` (every byte handed to the OS), the crash-point cuts of `TornSlotRewrite_Tests` and `TornWalAppend_Tests`; `exception`: `StickyFailure_Tests`, `CheckpointFailureWindow_Tests` (a promotion waiting on a failed checkpoint), `KeptJournalPromotion_Tests` (no promotion starts behind an earlier header journal), `SharedBufferedLogStream_Tests`, `TornWalAppend_Tests` (buffering caller logs), `DurabilityPolicy_Tests`, `AcknowledgedReopen_Tests`, `WrittenConfirmation_Tests`, `UnsyncedPromotion_Tests`, `CheckpointDataWriteFailure_Tests`, `Issue2821_Tests`, `Issue2242_UnsyncableLog_Tests`; `corrupt-input`: the 5.0.21 fixtures (`LegacyWal*`, `ConvertedWalBesideLegacyHeader_Tests`, `LegacyDamagedDocument_Tests`, `ForeignWal_5_0_21.zip`). Failing-before evidence: the `RegressionSince5021` tests fail on `dev`; each `IoSafety` repro was written failing and each fix mutation-checked. Regression proofs (`.github/safety/regression-proofs.json`, one per fixed bug that a black-box repro can reach): fifteen ReproRunner repros fail for the intended reason against the published LiteDB `6.0.0-prerelease.319` (built from `dev` `5dd942a7`, this PR's base; each also reproduces against that `dev` commit packed) and pass on the candidate: `Issue_3027_LegacyWalConversion`, `Issue_3027_LegacyDroppedIndex`, `Issue_3027_LegacyDamagedDocument`, `Issue_2242_UnsyncableStorage`, `Issue_3027_SharedMutexNameLength`, `Issue_3027_DumpInTransaction`, `Issue_3027_StreamDatabaseDispose`, `Issue_3027_LegacyReadOnlyStream`, `Issue_3027_ForeignLegacyWal`, `Issue_3027_TornWalAppend`, `Issue_3027_FailedSafepointWrite`, `Issue_3027_LostHeaderBesideWal`, and, with a device model built from caller streams in the repro (a stream that keeps only what a successful sync wrote, as the test suite's `SyncPowerLossModel`/`ForgetfulFile` do): `Issue_3027_OverwriteBehindUnsyncedLog` (a checkpoint's in-place overwrite behind a log that cannot sync: 19 of 22 power-loss images of the known bad lose rows the data file held), `Issue_3027_FailedHeaderSync` (fsyncgate: commits acknowledged durable after the recovery of a failed header sync lost at a power loss) and `Issue_3027_PromotionAfterFailedCheckpoint` (a compact insert that waited on a checkpoint whose data sync failed wrote a v12 header and re-synced the failed handle; forced deterministically through the caller stream's sync, 110 of 110 runs). These three also fail on the candidate with only their fix reverted. The permanent guards are the `LiteDB.Tests` tests they name. No proof: the durability decisions (3 to 6, 11, 13, 14) change behaviour rather than fix a bug; the per-write flush of caller streams, the encrypted partial-header restore and the written-confirmation outcome were introduced and fixed within this PR (`6.0.0-prerelease.319` has neither the header frame nor a commit outcome). Full suite and CI: see "Validation".
- **Coverage delta and residual concerns:** no test was skipped or quarantined. Tests whose expected behaviour a decision changed were renamed or split per mode; each has a disposition in `.github/safety/coverage-ledger.json` (`3027-*`), as do the AutoRebuild assertions that checked the old failing first open, the .NET Framework job's 30-minute limit and the fuzz corpus re-pins (four pinned seeds, bisected per commit: their traces changed only at `7f53e4539`, `2b4f1ac0f`, `e4b9553fd` and `042db3fa8`; every other pinned seed replays unchanged; the oracles pass and the hashes match on .NET 8 and .NET 10). New fault hooks are registered in `fault-points.json` with evidence. Residuals are listed under "Known residuals"; the strongest plausible counterexample is an ordering of unsynced writes across the two files that the power-loss models do not produce (they keep each file as of its last sync, not partial or reordered subsets, nor torn pages).

## Durability decisions (owner)

Recorded in [`docs/decisions/durability-policy.md`](https://github.com/litedb-org/LiteDB/blob/claude/compassionate-knuth-m52zj6/docs/decisions/durability-policy.md) (`822b17406`; second round `48c1c37c6` and `cee8bb3ee`; third round `b6da487fc` and `a2e966a8c`) and in LiteDB-Artifacts (`pull-requests/3027-io-regressions-since-5021/decisions.md`; the independent second opinion behind the third round is in `review-evidence/fable-second-opinion-2026-09-28.md`). All are implemented; the decisions document's implementation notes 1 to 16 say how, and the release notes and design docs follow them.

**Scope (earlier decisions, still in force)**
- Out of scope, best effort only: drive and memory defects, older LiteDB versions, and anyone else changing the database files while LiteDB runs.
- If LiteDB itself replaces or changes a file, it must handle that correctly.
- The same LiteDB version must "speak the same language" with itself, and that logic must not be able to go wrong.

1. **WAL clearing (strict rule).** The WAL, its header journal and any legacy header backup are removed only after a successful data sync covered every data write; otherwise fail closed. The WAL may grow instead; if that isn't possible, fail when trying to write. Volatile logs are exempt.
2. **Read-only fallback.** If reading is possible, allow it; writes throw a catchable `IOException`, and `$database` (`readOnly`, `readOnlyReason`, `writeFailure`, `walKept`) reports why without a write.
3. **A write that cannot be persisted fails loudly.** With `durable commits` on (the default), a commit whose WAL can't be synced throws before it writes a frame; it is never acknowledged as non-durable.
4. **Durable in the WAL but not in the data file is allowed.** WAL syncs continue while only the data file can't sync; the WAL grows up to `wal limit` (1 GiB by default); past it, writes throw and reads keep working, and each refused write retries the sync that failed.
5. **`durable commits=false`: the user is on their own.** No log sync at commit; no throw from an automatic checkpoint or `Dispose`; failures are reported through `$database`.
6. **A real failure is sticky, in both modes.** Recorded (file, operation, error, time, WAL kept); the engine continues read-only until reopened; the next write throws with the record.
7. **Temporary code** goes to this repo or LiteDB-Artifacts before it is thrown away.

Defaults: **A.** "Cannot sync" is no failure with `durable commits=false`. **B.** Disk full is a sticky failure. **C.** The sticky state lasts until reopened; shared connections keep it connection-wide. **D.** Opt-out users keep the strict WAL rule and the WAL limit.

Second round: **8.** the data header is anchored in the WAL (its condition replaced by 11); **9.** a WAL directory that cannot be synced or opened fails a durable commit loudly before it writes; **10.** the anchor is a header frame at the start of the WAL.

Third round: **11.** every WAL generation starts with the header frame, in both modes; an open restores a lost data header from it, never initializes a new database over a WAL that holds frames, or fails unchanged. **12.** no unsafe mode in this PR. **13.** the read-only reopen after an outcome-unknown commit shows only acknowledged commits while the files are as the failure left them; a later open lets the files decide. **14.** the data barrier before the first commit stays, best effort: once per process and data header in direct mode, once per shared connection, never per operation, and it never refuses a commit.

## Behaviour changes worth reviewing
- **Failures are sticky (decision 6).** A write or sync that failed is recorded and the engine continues read-only until reopened; before, it closed and every later call threw. A refusal before anything was written (a data file or, opted out, a log that cannot sync) is no failure. `:memory:` and `:temp:` stay closed after a write failure, as before (their streams go with the failed engine).
- **Fail-loud durable commits (decisions 3 and 9).** With durable commits (the default), a commit on a log or WAL directory that cannot sync throws before it writes a frame; `durable commits=false` is the opt-out. A failed commit carries `Exception.Data["LiteDB.CommitOutcome"]`.
- **No overwrite behind an unsynced log, in either mode (decision D).** Opted out on a log that cannot sync: checkpoints write nothing and keep the WAL (up to `wal limit`), compact writes stay BSON, a 5.x conversion or index migration opens read-only. Before, they proceeded without a power-loss guarantee.
- **The WAL grows while the data file cannot sync (decisions 1 and 4),** up to `wal limit` (1 GiB by default); past it, writes throw and reads work. `$database.walKept`, `logFileSize` and `walLimit` report it.
- **Every WAL starts with a header frame (decision 11):** one more frame per WAL generation. Older 6.x prereleases do not read it.
- **Engine stops** on a WAL write failure that may have left a torn frame, whatever the exception type (5.0.21 rolled back and kept going after a non-I/O failure); rollback-only transactions after a failed safepoint write.
- **Caller streams** are flushed once per WAL batch and per sync, as in 5.0.21. A reader that reads one while a batch or checkpoint is being written first flushes what it holds for the writer (at most one extra `Flush()` per page written, none without concurrent readers); a failure there fails the read as a write failure and the writer's batch.
- **Refusals (both files byte-identical):** `LOCK_TIMEOUT` for a blocked conversion; `INVALID_DATABASE` for a converted WAL beside a legacy header, a committed legacy WAL page that is not a page of its type or lies beyond both files, another database's header, or a WAL whose data file is gone or lost pages its header frame names.
- **`AutoRebuild`** rebuilds in the same open that detects damage. Non-writable streams holding a 5.0.21 file open read-only.
- **fsync cost on storage that syncs** (the same probe on `dev` `5dd942a73` and on this branch, Linux):

  | Scenario | `dev` data + log | This PR |
  |---|---|---|
  | Direct mode: open, 1 insert, dispose | 2 + 3 | 3 + 3 (the close checkpoint syncs the data file before it writes) |
  | Direct mode with `CHECKPOINT=0` | 0 + 1 | 0 + 1 |
  | Shared mode, per operation | 0 + 1 | 0 + 1 |
  | Full checkpoint | 2 + 2 | 3 + 2 |
  | Retiring partial checkpoint (first, second) | 3 + 8, 2 + 5 | 5 + 9, 3 + 6 |
  | First commit reusing retired slots | 0 + 1 | 0 + 1 (implementation note 15: reuse needs no sync of its own) |

  A failed commit whose confirmation was written syncs the log once more before it reports `NotCommitted` (that failure path only). A caller stream whose `Flush()` syncs is synced once per WAL batch and sync: the index-migration recovery harness's crash-at-commit case makes 3,352 syncs (`dev`: 3,348; 14,370 with the flush after every write this branch had from `c4119caba` until `063c83289`).

## Known residuals (documented)
- **Power-loss models** keep each file as of its last successful sync: one state per crash; they do not produce unsynced writes reaching disk in a partial or reordered subset across the two files, nor torn pages. `HeaderFrameCrash_Tests` adds the process-crash image (every byte handed to the OS).
- **Process-wide durable headers** assume a file at the same path with the same header is the same file: whoever replaces a database file must sync it (release notes; `FreshEngineDurability_Tests`).
- **Power-safe overwrite is assumed** (implementation note 16): a sector the device did not write keeps its old bytes.
- **A rebuild on storage that cannot sync:** a data file that cannot sync refuses the rebuild unchanged; where only its recovery marker or the directory cannot sync, the renames install the replacement without a power-loss guarantee, and the original files stay under their `-backup` names. Follow-up: #3049 (directory syncs where the storage has them: #3011).
- **Caller data streams other than a `FileStream`** are the caller's to sync (#3044).
- **WAL frames a failed log sync left in the OS cache only** ("fsyncgate"): a later process that opens the database before they are evicted replays that commit (outcome `Unknown`) and appends after it; a power loss before its first checkpoint also loses the commits it acknowledged since. The engine that saw the failure writes nothing more (decision 6). Follow-up: #3048 (durable commits after a reopen must not depend on an unproven WAL prefix).
- **A foreign legacy WAL** that commits no header, or that belongs to another copy of the same seed file, is still replayed, as in 5.0.21 (#3043).
- **Pre-existing on `dev`, not changed here:** a failed write of the sort spill file (a large `ORDER BY` on a full disk) closes the engine instead of failing only its query; a commit racing a concurrent `Rebuild` (#3042).
- **Encrypted files on a data file that cannot sync:** a writable open that would retire a kept header journal fails with the preamble's `FileSyncException` instead of opening read-only (an encryption preamble needs a successful sync, as documented); both files are unchanged.
