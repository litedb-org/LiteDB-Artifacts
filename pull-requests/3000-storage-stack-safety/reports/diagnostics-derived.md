# Historical failures and bounded follow-up evidence (derived)

This is a curated interpretation of retained reports, not raw CI output. Logs, full dumps, binaries, PDBs, environment dumps and machine paths remain outside this bundle. Negative results are retained as facts and linked to the original hosted evidence.

- Four initial corpus hash-drift failures (two checksum-crash seeds on each runtime) were retained before repinning. Fresh independent full-model runs and recorded-byte replay agreed across both runtimes before hashes changed. They are not silently counted as successful original runs.
- A shared-write diagnostic on the original Windows system-temp volume captured a durable data-header flush owner and three waiters on its mutex, without a captured cycle. Recovery preserved all 83 recorded returned inserts and verified 85 complete model documents. [Captured run](https://github.com/litedb-org/LiteDB/actions/runs/35783032832). The original undumped timeout remains individually unattributable.
- The corrected per-worker completed-progress watchdog retained five workers, 20 inserts each, C-volume/runtime/hooks guards and the 300-second session limit. [Campaign at 5447ffe45](https://github.com/litedb-org/LiteDB/actions/runs/35786782395) passed 100 cold hosts and two 53-case contract hosts. One natural successful run took 45.664 seconds, with workers completing in 42.354–42.698 seconds. The data/index oracle passed. This is bounded evidence, not universal liveness proof.
- Separate diagnostic test defects were corrected: a substring assertion rejected a valid PID-containing dump filename; real dump smoke capture needed a bounded retry around tool timing. All failed-attempt evidence was retained. The real worker-timeout capture remained single-shot with the original budget; the smoke test still requires an actually validated successful dump.
- [Index b204 CI](https://github.com/litedb-org/LiteDB/actions/runs/35790860650) finished 46 successful jobs and one Windows-latest x86/.NET 8 query-session timeout. It hit 300 seconds after 183 completed passing tests; the randomized overlap case had passed in 148 seconds. No assertion failure or original active-test trace exists for the abort. These are in-memory query fixtures, so no file-I/O explanation is claimed.
- [Two exact-binary cold diagnostics](https://github.com/litedb-org/LiteDB/actions/runs/35794826867) passed 813 cases plus one existing skip in 83.28/88.95 seconds. Same-runtime comparison sessions took 57–88 seconds. Independent local profiling identified expensive unordered ID assertions; strict Int32 sorted multiset comparison retains membership, duplicate multiplicity, generated cases, plan checks and separate Value ordering checks, with 14 negative/positive controls. See query-assertion-cost-derived.md. This supports the test-only efficiency change, not an exact retrospective cause for the historical slowdown.
- [Final index job at 95ba846e](https://github.com/litedb-org/LiteDB/actions/runs/35795806341/job/106976107809) passed its query session: 827 cases plus one existing skip (including two host guards), 46.510 seconds; randomized cases 0.622/0.489/0.127 seconds. Original b204 failure status is preserved.
- A compact-layer exact-type assertion rejected a valid PageChecksumException subclass before reaching its preservation oracle. The original run therefore did not prove unchanged bytes. The final correction checks data/WAL preservation before accepting only invalid-database, unsupported-version or checksum corruption categories. Six deterministic plain/encrypted controls and both original tears pass; a genuine journal must recover the same damaged primary with complete payload/index agreement. The initial two-code whitelist proposal also failed and remains part of the history. Final compact/top platform checks remain pending in the frozen snapshot; local passing tests do not replace them.

Independent review found no remaining concrete production safety finding in these investigations under the documented model, conditional on final-head validation. No blanket all-green claim is made here. CRCs are not authentication; hardware durability, arbitrary power faults and every execution are not proven by these finite tests.
