### #1706 (PR #2917) — OVERSHOOT (medium)

**[SUGGESTION] Improve query optimization**

- Need: Two logically identical LINQ queries — Where(x => x.Id >= low && x.Id <= high) vs Where(x => x.Id <= high && x.Id >= low), both OrderByDescending(Id).Limit(10) over 50k rows — ran 2x apart in wall time because the optimizer always picked the first indexable term, giving INDEX SCAN(_id >= 24900) in one case and INDEX SCAN(_id <= 25100) in the other. He wanted predicate order to stop mattering; in follow-up comments (after lbnascimento measured a BETWEEN plan as much faster than either) he asked LiteDB to fuse `x >= low && x <= high` into a single BETWEEN range scan.
- Gap: The BETWEEN fusion he asked for in the comments is not done — the second bound is still a filter evaluated after LoadDocument, so an unbounded (no-Limit) range query still loads every document from the chosen bound to the end of the index instead of the ~201 in the range. His filed benchmark uses Limit(10), so that is not blocking him, but the plan lbnascimento told him was the fastest is still unreachable except by writing `$._id between @0 and @1` by hand.
- Overshoot: HasCloserStart only optimizes the scan prefix and ignores where the scan terminates. IndexCost.CreateIndex builds `>= v` as IndexRange(v, MaxValue) and `<= v` as IndexRange(MinValue, v), and IndexRange.Execute runs to the natural end of the index. For ascending order — the default whenever OrderBy does not match the index expression — the lower bound now always wins, so previously bounded scans become full-tail scans: col.Find(x => x.Id <= 100 && x.Id >= 1) on 50k rows went from INDEX SCAN(_id <= 100) (100 nodes) to INDEX SCAN(_id >= 1) (50k nodes scanned, 50k documents loaded by QueryPipe, then filtered to 100). Same for `key BETWEEN 1 AND 5 AND key > 3`, where the unbounded `key > 3` is now preferred over the bounded BETWEEN. Reversed_range_terms_seek_from_the_output_start pins this by asserting the ascending plan contains "key >", and only exercises it through Limit(5) where the choice is harmless. Before the commit users could steer this by predicate order (the workaround this issue thread itself taught); that control is now gone and the regression is silent. Separately, LiteDB/Utils/BsonNumberComparison.cs is dead code — grep at 304ccad2f9 finds only its definition — duplicating IsDecimalConvertible/OutOfDecimalRangeSign already present in the parent commit, and Issue1706NumericBounds_Tests.cs tests that pre-existing behaviour rather than anything this commit changes.
- Suggested: Narrow the tie-break: apply PreferRangeStart only when the query has a Limit or Offset (where prefix waste is what costs), or make it compare expected scan span rather than only the start point so a bounded range (BETWEEN, or the tighter single bound) is never replaced by one that runs to the end of the index. Better still, do what the reporter asked and fuse two compatible bounds on the same index into one IndexRange, keeping the independent multikey ANY case excluded as the existing comment notes. Drop BsonNumberComparison.cs and Issue1706NumericBounds_Tests.cs from this commit — they belong to the earlier mixed-type comparison change. Then reply on the issue: predicate order no longer changes the plan, but BETWEEN fusion is still open, so `$._id between @0 and @1` remains the fastest form for a bounded range without a limit.

### #2820 (PR #2918) — OVERSHOOT (medium)

**Opening a file that is not a v5 LiteDB database modifies it: files under 8 KB are overwritten with an empty database, larger ones are truncated**

- Need: #2820 consolidates three real reports: #2277 (an app probes files with `new LiteDatabase(path)` and falls back to an old serializer on exception — LiteDB rewrote the old files), #2434 (a v4.1.4 db opened on 5.0.18 without `Upgrade=true` throws and is left truncated, afterwards unopenable by v4 or v5 even with Upgrade), #2501 (a 16-byte text file is opened and written to; a ~16 KB one throws after truncation). All three want the same thing: a failed open must throw and leave the file byte-identical, and a v4 file must still be upgradeable afterwards.
- Gap: #2434's reporter still gets the generic "File is not a valid LiteDB database format or contains a invalid password" for a v4 file. The issue's own item 4 (detect a v4 header and say "v4 data file, open with Upgrade=true") is not implemented, so a user holding a v4 file still has to find `Upgrade=true` themselves — the file is no longer harmed, but the message does not point at the remedy.
- Overshoot: `allowRecovery: false` is passed from every engine path (FileStreamFactory and StreamFactory, data file, log file and temp/sort file), which silently reverts closed issue #2343. #2343's corrupted file is exactly 8192 bytes with byte 0 = 1, salt at 1..16 and zeros from 17 on; AesStream recovered it via `isNew = checkBuffer.All(x => x == 0)` at offset 32..64. That branch is now `if (isNew && !allowRecovery) throw LiteException.InvalidDatabase()`, so such a file is permanently unopenable instead of self-healing. Because `CreateLogFactory` uses the same password and factory, an interrupted `.log` creation now hard-blocks opening a database whose `.db` holds real user data. Second guard: `!allowRecovery && Length > 0 && Length < PAGE_SIZE` throws for a partially written encrypted preamble (e.g. 17 bytes) — the very case #2820 item 3 says to keep re-initialising ("This keeps the existing recovery case from #2343"), and it makes `FileStreamFactory.GetLength`'s partial-preamble branch (returning 0 when the first byte is 1 and length < PAGE_SIZE) unreachable as a recovery path. No test in the commit shows a legitimate interrupted-creation file still recovering; instead `OpenValidation_Tests` InlineData(16384, "secret", …) pins the opposite by building the zeroed-32..64 shape and asserting INVALID_DATABASE. Minor extra cost: every open of an existing database now reads and parses page 0 twice (DiskService then LiteEngine).
- Suggested: Narrow the AesStream change rather than revert it: keep recovery allowed for the writable stream that DiskService opens when it has already decided the file is new/partial-preamble (or pass the decision down explicitly), and keep `allowRecovery: false` only for the validation/read path used to reject foreign files. Add a regression test for the #2343 shape (8192-byte encrypted file with 32..64 zeroed, created by LiteDB) still opening, and either honour or delete the now-dead partial-preamble branch in `FileStreamFactory.GetLength`. Separately, implement issue item 4 (v4 header detection with "open with Upgrade=true") or post that sentence as a comment on #2434 so its reporter knows the remedy.

### #1087 (PR #2916) — PARTLY_UNBLOCKED (medium)

**Concurrency on Linux platform**

- Need: Running LiteDB (v4) on .NET Core 2.0 on Linux, concurrent file access in exclusive mode with the default timeout failed instead of waiting. They diagnosed it precisely: `IOExceptionExtension.IsLocked()` masks the HResult into a Win32 error code, but on Linux the IOException carries the raw errno (11, EAGAIN/EWOULDBLOCK), so the retry loop rethrew immediately rather than waiting. Their own patch was "compare HResult with 11". Two later commenters (Jaben, petermicuch) report the same v4 stack trace under Docker — same defect, different environment.
- Gap: The reporter's real goal — concurrent/exclusive file access from Linux — is not demonstrably served by this change on v5. The two live callers of the patched helper are `RebuildService` (`File.Move`, 5 s) and `DiskService.MarkAsInvalidState` (header write, 60 s); the v4 path in their and Jaben's traces (`FileDiskService.Lock` → `LockService` → `StreamExtensions.TryLock`) no longer exists. `FileHelper.IsFileLocked` is now correct on Linux but its only consumer, `FileStreamFactory.IsLocked()` / `IStreamFactory.IsLocked`, is never called in production. Opening the data file (`FileStreamFactory.GetStream`) is not wrapped in any retry, so a second process still fails immediately with no retry and no guidance. Nobody has told the reporter that v5's answer for multi-process on Linux is `Connection=Shared` (named mutex). macOS/BSD report errno 35 for the identical condition and are still unhandled, and the test pins "only on Linux" as the expectation.
- Overshoot: Small but real: on Linux any `IOException` with `HResult == 11` is now "locked", not only flock/share violations. EAGAIN/EWOULDBLOCK also arrives from non-blocking FIFO/pipe/NFS I/O, so `DiskService.MarkAsInvalidState` can now spin for up to 60 s during an error-close dispose (and `RebuildService`'s `File.Move` up to 5 s) where it previously threw at once. `FileHelper.IsFileLocked` flips false→true on Linux, but has no production consumer, so no blast radius there. No new public API, no new exception types, no default changes, and the extra `IsOSPlatform` check only runs on an exception path after the two existing comparisons fail.
- Suggested: Comment on the issue with an honest answer: (1) the errno-11 detection you proposed is now in (`9a011a94`), guarded to Linux; (2) but the v4 machinery in your trace (`FileDiskService.Lock`/`LockService`, per-operation file lock + retry) was removed in v5 — in v5 the helper is only reached by database rebuild and error-close, so on v5 the errno fix alone is not what makes concurrent access work; (3) for multi-process access on Linux in v5 use `Connection=Shared`, which serialises through a named mutex. Also open a follow-up issue for macOS/BSD, where the identical flock failure reports errno 35 and `IsLocked` still returns false — the current test actively pins "only on Linux".

### #1904 (PR #2917) — PARTLY_UNBLOCKED (medium)

**[BUG] Quering Based On Referenced Entity Failed After Creating The Index**

- Need: On LiteDB 5.0.9, `humans.Include(h => h.Homes).Query().Where(Query.Any().EQ("$.Homes[*].Value", 655555))` returned the right Humans until he ran `humans.EnsureIndex("$.Homes[*].Value")`; after that the same query returned nothing. He wanted correct results *and* an index he could lean on, because (his later comment) the two-step workaround "will degrade the performance to the worst level when using pagination". He also asked, unanswered, how to query a named index explicitly (`EnsureIndex("home_value", ...)` then `Query.GTE("home_value", 0)`), noting it does not work even for plain nested arrays.
- Gap: The index he created is now silently a no-op: the planner skips it and full-scans `_id`, resolving every reference per document. Nothing tells him — no exception, no warning at `EnsureIndex`, and only `GetPlan()` reveals the fallback. So his actual goal (indexed, paginated queries over a `[BsonRef]` field) is still unreachable and he has no way to learn that from the library; he will keep creating indexes that do nothing. His second question (how to use a named index explicitly, including for plain nested arrays) is untouched by the commit.
- Overshoot: The exclusion is conservative by design: `IncludeChangesIndex` returns true (drop the index) whenever `TryGetMemberPath` cannot parse the expression, so indexes that are actually valid get dropped too — filtered-array paths (`$.refs[@.x=1].$id`), function- or arithmetic-wrapped paths (`LOWER($.ref.$id)`), and any index over `$`, which is now excluded for *every* query that carries any INCLUDE. Those users silently lose a working index plan (index seek → `_id` full scan) with no diagnostic. The same applies to ORDER BY: `Issue1904Planning_Tests` pins that an order-by on an included field no longer reuses the index and falls back to an explicit (possibly disk-backed) sort. The `BasePipe` change also broadens `_id` exclusion from exact to case-insensitive, i.e. a referenced document with an `_ID` field silently stops contributing it — beyond anything the report needs (a later commit in the same PR, #1920, reworks that line again). Planning tests also assert internal plan names, e.g. that a non-include query still uses `reference_value` and matches `$.ref.value = null` for 2 rows, pinning stale-stub indexing as guaranteed behaviour.
- Suggested: Comment on #1904 with the honest answer: (1) his query returns correct results again with the index present — fixed in #2917, covered by `LiteDB.Tests/Issues/Issue1904_Tests.cs` using his exact `Human`/`Home` model; (2) an index on a `[BsonRef]` field can never accelerate anything, because the parent document only stores `{$ref,$id}` — the planner now skips such indexes instead of returning wrong results, so he should drop `EnsureIndex("$.Homes[*].Value")`; (3) for indexed pagination, either index `Value` on the `Homes` collection and drive the query from there via `$.Homes[*].$id ANY = ...` (which *is* still index-backed after this fix), or denormalize `Value` onto `Human`; (4) LiteDB 5 has no "query by index name" — you query by expression and the planner matches an index whose expression is textually identical, which is why `Query.GTE("home_value", 0)` never worked. Separately, consider a follow-up issue for surfacing the skip (warn or throw on `EnsureIndex` over a `BsonRef` path, or expose it in `GetPlan`), and for narrowing the conservative `TryGetMemberPath` fallback so function-wrapped and filtered-array indexes are not dropped wholesale.

### #2357 (PR #2917) — PARTLY_UNBLOCKED (high)

They expect the insert to work (presumably with LiteDB filling the id, Mongo-style); instead it throws `InvalidCastException` from `LiteDB.ObjectId` to `System.String`. No comments from anyone else; single scenario.
- Gap: The reporter still cannot run their code. `col.Insert(new RoflType("MyName"))` now throws `LiteException` "Data type System.String is not assignable from data type LiteDB.ObjectId" instead of `InvalidCastException`. That message never mentions the member name (`Id`), never says the trigger was auto-id generation, and never says what to do. Two facts they need are nowhere: (1) their `string.Empty` Id is turned into BSON null by `BsonMapper.EmptyStringToNull` (default true), which is what makes LiteDB think an id must be generated — a non-empty string Id works fine, an empty one fails, and nothing in the message explains that asymmetry; (2) LiteDB has no string auto-id, so they must assign `ObjectId.NewObjectId().ToString()`/`Guid.NewGuid().ToString()` themselves, switch `Id` to `ObjectId`/`Guid`/`int`, or install a custom `ResolveMember` setter. That last escape hatch is the one the commit deliberately preserves (`_id.Setter == _id.DefaultSetter` guard, exercised by `AutoIdAssignment_Tests.Custom_setter_can_copy_back_ObjectId_to_a_string_member`) but it is undiscoverable from the exception. The issue is still OPEN with zero comments, so the reporter has had no answer at all since 2025-02-19.
- Overshoot: Three changes go past what #2590 needs (they serve the other issues bundled in the same commit, #1002/#2811): 1. `id.IsNull ||` was added to the Int32, Int64 and Guid branches of `RemoveDocId` (LiteDB/Client/Database/Collections/Insert.cs:95-98). Previously `int?`/`long?`/`Guid?` ids left as null reached the engine and threw `LiteException.InvalidDataType("_id", Null)` (LiteDB/Engine/Engine/Insert.cs:67); now they silently auto-generate. Behaviour flip on a path that used to throw — fine as a fix, but not asked for here, and pinned by `AutoIdAssignment_Tests.Nullable_ids_generate_for_null_and_empty_and_survive_reopen`. 2. The id copy-back setter now runs *inside* the engine's lazy enumeration, mid-transaction (the new `GetBsonDocs(T, BsonDocument)` iterator). A user-supplied Id setter that throws now aborts the ambient transaction: `AutoIdAssignment_Tests.Throwing_setter_rolls_back_before_caller_can_commit` pins that `db.Commit()` returns false after an explicit `BeginTrans()`, so unrelated work already queued in that user transaction is discarded too. Previously the row committed and only the setter blew up. Defensible, but it is a semantic change for every `Insert`/`Upsert`/`InsertBulk` caller, not just this reporter. 3. `MemberMapper.DefaultSetter` added (internal, so not public API surface) purely to let the new check distinguish a user-supplied setter. The Issue2590 test itself hedges: it accepts *either* a working string auto-id *or* the rejection, and only the rejection branch actually executes — so it does not pin that the reporter gets what they asked for.
- Suggested: Comment on #2590 with the honest answer the reporter never got, then close (or keep open only for the message wording): "LiteDB auto-generates `_id` only for ObjectId, Guid, Int32 and Int64. Your `Id` is a `string`, and because `BsonMapper.EmptyStringToNull` is on by default your `string.Empty` is stored as BSON null, which makes LiteDB think it must generate an id — it generates an ObjectId and cannot assign it back to a string. Fixes: assign the id yourself (`Id = ObjectId.NewObjectId().ToString()` or a Guid string), change `Id` to `ObjectId`/`Guid`/`int`, or register a custom `mapper.ResolveMember` setter for `Id` (see AutoIdAssignment_Tests.Custom_setter_can_copy_back_ObjectId_to_a_string_member)." Separately, make the new throw in Insert.cs:110 self-explanatory the way the read-only-member throw two lines above it already is — name the member and the cause, e.g. "Cannot generate an auto ID for member 'Id': generated ObjectId values cannot be assigned to System.String. Assign the id yourself or map it with a custom setter." Keeping the plain "Data type X is not assignable from data type Y" text is the one thing that leaves this reporter guessing.

### #2814 (PR #2918) — PARTLY_UNBLOCKED (high)

**Log file (-log.db) grows without bound when other transactions are always open, because auto-checkpoint is skipped instead of retried**

- Need: Users running a shared LiteDatabase with a steady writer plus continuous concurrent readers (#2125: bulk InsertBulk with 50 FindById tasks; #1764: 6 GB log in hours; #2261: always-on service) saw the -log.db grow until the disk filled, because auto-checkpoint was skipped on every commit whenever any other transaction was open. They wanted the log to be checkpointed back into the data file on its own, without having to call db.Checkpoint() manually or restart the process.
- Gap: No hard cap: any transaction that stays open longer than the 10 ms admission wait (explicit BeginTrans held open, a lazily-enumerated Find cursor consumed slowly, a long write transaction) still starves auto-checkpoint completely, and the log still grows without bound — the commit's own evidence file says so ("explicit/writing/retained transactions may time out and later commits retry. No hard WAL cap") and Issue2814Lifecycle_Tests/Issue2814Backoff_Tests pin that the log stays non-zero while a reader is held. The 10 ms wait is also not escalated as the log grows, so a workload of continuous medium-length queries (each >10 ms) keeps failing admission; attempts are then rationed to once per 50 ms..1 s. Nothing warns or logs when this happens, so an always-on user like #2261 still has to work out on their own that they need periodic db.Checkpoint(). The issue's own second ask — document checkpoint behaviour on the pragma docs page — was explicitly excluded (only LiteDB.ReproRunner/README.md was touched).
- Overshoot: Modest and bounded, no new public API, no new exceptions, no changed defaults. (1) Read latency cost everyone with concurrent readers now pays: while the committing thread waits up to 10 ms for exclusive admission, TransactionGate blocks all new reader leases (_waitingWriters != 0), so read-heavy callers can see up to 10 ms stalls where previously the checkpoint attempt aborted instantly with zero reader impact; CheckpointBackoff rations this to one waiting attempt per 50 ms..1 s only after a failure, and resets on every success. (2) The non-rationed TryCheckpoint() on the Dispose path (LiteEngine.cs:199) now also waits for readers instead of skipping — benign, arguably desirable. (3) Issue2814_Tests asserts a peak log size <= 8 x soft limit under 4 live reader threads; that is a timing-dependent bound that may flake on slow or loaded CI (this repo already has known ARM64 flakes). (4) TransactionMonitor.GetTransaction reordering (lease before ID reservation) is a real correctness companion to the change, not scope creep.
- Suggested: Comment on #2814 stating the scope honestly: auto-checkpoint is now admitted between short concurrent readers, so the #2125-style writer+FindById workload keeps a bounded log; but a transaction held open longer than the ~10 ms admission wait (explicit BeginTrans, a slowly consumed Find cursor, a long write transaction) still starves the checkpoint and the log still grows unbounded, with periodic db.Checkpoint() remaining the workaround. Then close the issue's two remaining items separately: the pragma documentation update, and a decision on whether a hard WAL limit / pragma (the issue's original proposal) is wanted for the long-transaction case.

### #2822 (PR #2918) — PARTLY_UNBLOCKED (high)

**Explicit transactions are bound to the OS thread, so BeginTrans/Commit/Rollback across await act on the wrong transaction**

- Need: 2822 is a maintainer-written consolidation of real user reports (#1771: `Commit()` returns false after an `await` and the writes are silently lost; #2373: ASP.NET Core/gRPC needs more than one transaction per thread; #2363: ThreadLocal tracking breaks async). Users want an explicit transaction that survives a continuation hopping threads — or, failing that, to not lose data silently and to be told what to do instead.
- Gap: The worst symptom listed in the issue is not fixed and the commit's own doc admits it: "This guard cannot distinguish two logical tasks that reuse a thread which already owns a transaction." The issue's headline repro — task A begins on T1, task B begins on T2, then B's `Rollback` runs on T1 and discards A's work while A's `Commit` commits B's — still behaves exactly as reported, because the guard only fires when the calling thread's slot is empty. That is the "wrong results" case the issue is labelled `severity: high` for, and it is the first item in the issue's own "Regression tests" list; there is no test for it. #2373 (several transactions per thread, gRPC) and the ENSURE crash are untouched. #1771's reporter now gets a loud, actionable error instead of lost data, but their actual goal — `await` inside a transaction — is still impossible and deferred to the long-term `ILiteTransaction` work. The new exception uses `LiteException(0, ...)`, so callers cannot catch it by error code and must match on message text.
- Overshoot: Mostly bounded, but three things go past the report. (a) `Commit()` throwing where it returned false is a behaviour break with no opt-out: any multi-threaded app with a defensive/unconditional `db.Commit()` in shared helper code now gets an exception whenever another thread happens to hold an explicit transaction. The issue did ask for this, so it is sanctioned, but it is a breaking change in a non-major line. (b) SharedEngine's `RejectAbandonedTransaction` is a genuinely new failure mode that the report never asked for: it is called from `OpenDatabase`, i.e. from ordinary reads and writes, not just from `Commit`, and it disposes the engine and throws when the transaction owner thread exited. Previously those operations proceeded on the orphan engine. (c) Asymmetry: the issue proposed that both `Commit()` and `Rollback()` throw; only `Commit()` does. The reasoning is sound and documented, but it means the issue text and the shipped behaviour disagree. The `_monitor.Transactions` snapshot scan is short-circuited to the failure path only, so no steady-state perf cost. Two pre-existing tests (Issue1344*) were relaxed to stop calling `Rollback()` after a successful `Commit()`; that path does not actually throw under the new code, so this looks defensive rather than a regression.
- Suggested: Comment on #2822 (keep it open) stating plainly which symptoms the commit covers and which it does not: fixed = "Commit() after a thread hop silently returns false and loses writes" (now throws with instructions) and the shared-mode abandoned-owner case; NOT fixed = the two-thread A/B interleave where the completing thread already owns its own transaction (still silently acts on the wrong transaction), multiple transactions per thread (#2373), and async transactions generally. Also record that `Rollback()` intentionally still returns false rather than throwing, deviating from the proposal in the issue body, so readers of that proposal are not misled. Optionally give the new exception a dedicated `LiteException` error code instead of 0 so callers can catch it.

### #2849 (PR #2918) — PARTLY_UNBLOCKED (medium)

**Large single-transaction inserts and deletes are 3-4x slower since the 1,000-page default (safepoint cost)**

- Need: The reporter (the maintainer, self-filed) measured that after #2772 lowered the per-transaction page limit to 1,000, one large insert went from 2.8s to 8.6-12.9s and a large delete from 1.8s to 7.1-8.0s at default settings, while `transaction pages=100000` restored 3.4s/2.2s. They did not want the default raised back; they wanted the safepoint itself made cheaper (profile it, avoid re-writing unchanged pages, avoid a flush per safepoint, consider scaling the limit with the cache budget) plus a benchmark to track it.
- Gap: Residual regression. The commit's own evidence (`docs/open-bugs/evidence/2849-manual-20260917.json`, 1M rows, Linux/net8/Release) still shows default vs `transaction pages=100000` at 1.83x for insert (33.1s vs 17.5s) and 1.65x for delete (25.6s vs 14.4s) — down from the reported 2.5-3.8x, but roughly half the regression remains, and the default is still clearly slower than pre-#2772. Three of the four directions the report itself proposed are untouched by this commit: skip re-writing a page that has not changed since its last persisted copy, avoid a flush per safepoint (#2818 in the same PR touches flushing, not this axis), and scale the page limit with the cache budget instead of the fixed 1,000 (`MemoryProfileDefaults.GetTransactionPageLimit` unchanged). The benchmark the report explicitly asked for ("Add a benchmark (large insert, DeleteMany over random keys) to track this") was not added — nothing in `LiteDB.Benchmarks/` references this, so nothing guards the remaining gap or a future re-regression. The evidence file also contains no pre-change measurement from the same harness, so the size of this commit's own win is inferred by comparing ratios across different machines and datasets. Meanwhile PR #2918 lists "Closes #2849", which would mark a partially-recovered perf regression as fixed.
- Overshoot: Small and mostly contained. `TakeIdleWritableLocked` (LiteDB/Engine/Disk/MemoryCache.Writable.cs:80-97) mirrors what `EvictLocked`/`TransitionToFreeLocked` (MemoryCache.cs:261-309) already did — `_index.Remove`, `_sharedReads.Forget`, `Generation++` — so stale `BufferSlice`s throwing after the transfer is pre-existing eviction semantics, not a new failure mode. No public API, no changed default, no new validation, no new exception on a path that used to work. The one cost others pay: a write to a page that is momentarily idle in the read cache now removes that cache entry, so the next reader of that position takes a disk read where it previously got a cache hit (the old code kept the readable copy and memcpy'd). For read-while-write workloads on hot pages that is a real, unmeasured trade-off; the PR measures read throughput and working set (79 -> 76 MB) but not this specific effect. Test churn in `Cache_Tests`/`FrameFailure_Tests` (moving `source.Release()`, `PinnedPages` 0 -> 1) is a consequence of the new hit path, not an unjustified expectation.
- Suggested: Before merging, drop "Closes #2849" from PR #2918 and leave the issue open (or close it and immediately file the follow-up), because the commit recovers roughly half the regression. Post on #2849 the same-harness before/after numbers for this commit alone — the evidence file only has post-change default vs large-budget — and state plainly that the default remains ~1.65-1.83x the large-budget setting, that `transaction pages=100000` is still the escape hatch, and that the unchanged-page-skip, per-safepoint flush and cache-budget-scaled limit ideas plus the requested insert/DeleteMany benchmark are still open.
