# Shared handle callback versus native writer ownership

Proves [review 5367523337](https://github.com/JKamsker/LiteDB/pull/133#pullrequestreview-5367523337) against the unmodified production package of actual reviewed commit `12a057424843d54bf10a53318433c889a7db025d`.

Six individually isolated child cases cover plain/null-password and encrypted databases with (1) an input enumerable calling ordinary `db.UserVersion`, (2) that callback writing an unrelated collection, and (3) a late transaction-bound reader's `ReadTransform` calling the ordinary pragma getter. The child startup handshake precedes execution; neither process startup nor an unqualified timeout counts as reproduction.

After the application callback starts, another thread observes the receiving parent's existing `_mutexWaiters` field and calls its existing turnstile `HasWaiter()` zero-time native probe. A positive waiter count, occupied turnstile, and waiting application thread establish the native admission boundary. The fixture uses a fresh database and parent wrapper and introduces no other native waiter before this observation. These are read-only reflection observations of production state, not TESTING hooks, instrumentation, or replacement known-bad binaries. The known-bad outcome additionally requires that operation remain incomplete for one second after that boundary, then verifies that external session cancellation unwinds it with `OperationCanceledException` and releases ownership.

The fixed operation catches `InvalidOperationException` inside the application callback, confirms the handle remains Active and its earlier insert remains visible, and commits (input callbacks) or rolls back (late reader). All cases then require a separate process to commit a row, followed by two cold Direct opens checking the exact record model, actual value-index seek plans/results, absence of an ordinary unrelated write, and an untouched sentinel. The cancelled known-bad case also undergoes peer progress and cold verification after its forced unwind.

Eight plain/encrypted controls verify independent work in another Shared database, Direct independent callback reads and writes without implicit enlistment, completion of an idle handle on another thread while an ordinary caller waits, and cancellation of ordinary Shared admission while another session continues to retain writer ownership. The latter intentionally separates the owning and cancelled sessions so writer release cannot race cancellation and make the expected cancellation outcome ambiguous.

Strict outcomes: `0` and `BUG_REPRODUCED` for the pinned package; `10` and `VERIFIED_FIXED` for the candidate. Every case and control must agree. Setup, startup, missing reflection members, ambiguous waits, unexpected exceptions, and data-model failures return `2`. Database paths remain on the system temporary volume and are printed for retention. The proof establishes bounded concurrency and cleanup behavior; it does not simulate power loss.
